# コーディング規約

## コメント

- コメントは「なぜ（Why）」を書くために使う。コードを読めばわかる「何を（What）」「どのように（How）」は書かない
- 自明な処理にはコメントを書かない。関数名・変数名・型で意図が伝わるならそれで十分とする
- 書くべきもの: 仕様上の制約や背景、非自明な判断の理由、採用しなかった代替案、既知の落とし穴やワークアラウンド
- コメントは短く保つ。長い説明が必要に感じたら、命名や関数分割で表現できないかを先に検討する
- 実装を言い換えただけのコメントや、変更履歴（「〜を修正」「〜を追加」）はコメントに残さない。履歴は Git と PR に残す
- 公開 API の doc コメント（Go の exported 識別子など）は Lint の要求に従って書くが、名前の繰り返しに留めず、利用者が知るべき前提や制約を書く

## テスト

- ユニットテストは、分岐や判定を含み、複数の箇所から再利用されるロジックに書く（例: ドメインルールの判定、期間・日付の計算）
- フィールドを詰め替えるだけの変換や、ライブラリ・生成コードを呼ぶだけの処理にはユニットテストを書かない
- テストケースは、入力の同値クラスと境界値を代表する最小限に絞る。同じ分岐を通るケースを並べない
- 複数のケースはテーブル駆動テストにまとめ、ケース名で何を検証しているかがわかるようにする
- 実装の内部構造ではなく、入力に対する出力や振る舞いを検証する
