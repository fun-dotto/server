# ユーザー向け MCP サーバー（User MCP）

## 背景

学生が Claude や ChatGPT などの AI アシスタントから、Dotto のデータ（時間割、休講・補講・教室変更、履修、科目など）を参照・操作できるようにしたい。
AI アシスタントは [Model Context Protocol（MCP）](https://modelcontextprotocol.io/) のリモートサーバーを「コネクタ」として追加でき、追加時に OAuth でユーザーを認可する。

現状、学生向けの API は App API（Connect、`cmd/app-api`）で、Firebase Authentication の ID トークンと Firebase App Check で認証している。
MCP クライアントは App Check トークンを発行できず、Firebase の ID トークンを直接扱うこともできない。そのため、App API を MCP クライアントにそのまま公開することはできない。

## 基本方針

- 新しいサービス **User MCP**（`cmd/user-mcp`）を Cloud Run に追加する。トランスポートは MCP の **Streamable HTTP**（ステートレス）にする。
- 実装には公式の Go SDK（`github.com/modelcontextprotocol/go-sdk`）を使う。
- ツールの中身は **App API の `handler.Handler` をプロセス内で呼び出して**再利用する。DB は直接参照するので、App API へのネットワーク越しの呼び出しはしない。業務ロジックを二重に持たない。
- 認可は MCP 仕様（2025-11-25）に従い **OAuth 2.1** にする。User MCP 自身が**認可サーバー（AS）とリソースサーバー（RS）を兼ねる**。ユーザーのログインには Web（fun-dotto.com）の Firebase Authentication を使う。
- アクセストークンは User MCP が発行する**不透明トークン**で、DB にはハッシュだけを保存する。Firebase の ID トークンは MCP クライアントに渡さない。
- 参照に加えて、**履修登録の追加・削除とユーザー設定（学年・コース・クラス）の更新**も提供する。書き込みはスコープで分ける。

### 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| App API に MCP エンドポイントを相乗りさせる | App Check 前提の Interceptor と認証方式が混ざる。障害やスケールの影響範囲も分けたい |
| MCP サーバーから App API を Connect クライアントとして呼ぶ | ホップが増え、サービス間認証の仕組みも増える。handler はプロセス内で再利用できる |
| 個人アクセストークン（Web で発行して手で貼る） | Claude.ai などのコネクタ UI は OAuth を前提にしている。トークンの手動管理は学生には難しい |
| Firebase Auth（Identity Platform）を OAuth AS として使う | Firebase は OAuth 2.1 の AS（Dynamic Client Registration や PKCE を備えた authorize/token エンドポイント）を提供していない |
| 外部の AS（Auth0 など）を使う | 新たな有料 SaaS と、Firebase とのユーザー連携が必要になる。必要な AS の機能は小さいので自前で持てる |

## 全体構成

```
MCP クライアント（Claude / ChatGPT など）
   │  ① POST /mcp（トークンなし）→ 401 + WWW-Authenticate（resource_metadata）
   │  ② GET /.well-known/oauth-protected-resource
   │  ③ GET /.well-known/oauth-authorization-server
   │  ④ クライアント登録（CIMD または POST /oauth/register）
   │  ⑤ ブラウザで GET /oauth/authorize（PKCE S256）
   ▼
User MCP（mcp.fun-dotto.com, Cloud Run）
   │  ⑥ 302 → Web の同意画面 https://fun-dotto.com/mcp/authorize?request_id=...
   ▼
Web（fun-dotto.com）
   │  ⑦ Firebase Auth でログイン → 同意画面
   │  ⑧ POST /oauth/authorize/complete（Firebase ID トークン + request_id + 同意結果）
   ▼
User MCP
   │  ⑨ 認可コードを発行し、302 → クライアントの redirect_uri
   │  ⑩ POST /oauth/token（code + code_verifier）→ access_token / refresh_token
   │  ⑪ POST /mcp（Authorization: Bearer <access_token>）→ ツール実行
   ▼
handler.Handler（internal/modules/appapi/handler）→ PostgreSQL / microCMS
```

## 変更点

### 1. エンドポイント（`cmd/user-mcp`）

| メソッド・パス | 内容 |
| --- | --- |
| `POST /mcp` | MCP の Streamable HTTP エンドポイント。Bearer トークンが必須 |
| `GET /mcp` | SSE は使わないため `405 Method Not Allowed` を返す（ステートレス） |
| `GET /.well-known/oauth-protected-resource` | Protected Resource Metadata（RFC 9728）。`resource`、`authorization_servers`、`scopes_supported` を返す |
| `GET /.well-known/oauth-authorization-server` | Authorization Server Metadata（RFC 8414）。`code_challenge_methods_supported: ["S256"]`、`client_id_metadata_document_supported: true` などを返す |
| `POST /oauth/register` | Dynamic Client Registration（RFC 7591）。CIMD 非対応のクライアント向け |
| `GET /oauth/authorize` | 認可リクエストを検証して保存し、Web の同意画面へリダイレクトする |
| `POST /oauth/authorize/complete` | Web から呼ばれる。Firebase ID トークンを検証して認可コードを発行し、リダイレクト先を返す |
| `POST /oauth/token` | `authorization_code` と `refresh_token` のグラント |
| `POST /oauth/revoke` | トークンの失効（RFC 7009） |
| `GET /healthz` | ヘルスチェック |

- `401` の応答には `WWW-Authenticate: Bearer resource_metadata="https://mcp.fun-dotto.com/.well-known/oauth-protected-resource", scope="..."` を付ける。スコープが足りない場合は `403` と `error="insufficient_scope"` を返す。
- リソース識別子（RFC 8707 の `resource`）は `https://mcp.fun-dotto.com/mcp` とする。トークンにはこの audience を紐づけ、異なる `resource` の要求は拒否する。

### 2. OAuth の仕様

#### クライアント登録

- **Client ID Metadata Document（CIMD）** を優先して扱う。`client_id` が HTTPS の URL の場合は、そのドキュメントを取得して `redirect_uris` と `client_name` を得る（結果は短時間キャッシュする）。取得先は SSRF 対策として、公開 IP の HTTPS に限り、サイズとタイムアウトにも上限を設ける。
- CIMD に対応しないクライアント向けに DCR も受け付ける。登録できるのは public client（`token_endpoint_auth_method: none`）だけにする。
- `redirect_uri` は、HTTPS か、ループバック（`http://127.0.0.1:*` / `http://localhost:*`、ポートは任意）に限る。

#### 認可

- 認可コードグラントと PKCE（S256）を必須にする。`plain` と implicit グラントは受け付けない。
- `/oauth/authorize` はパラメータ（`client_id`、`redirect_uri`、`state`、`code_challenge`、`scope`、`resource`）を検証し、`oauth_authorization_requests` に 10 分の有効期限で保存する。その上で Web の `/mcp/authorize?request_id=<id>` へリダイレクトする。
- Web は Firebase でログインさせ、クライアント名・要求スコープ・リダイレクト先のホストを表示して同意を取る（Web 側の変更は Web リポジトリで行う）。
- 同意後、Web はブラウザから `POST /oauth/authorize/complete` に `{request_id, firebase_id_token, approved, scopes}` を送る。User MCP は Firebase Admin SDK で ID トークンを検証して、uid を確定する。
  - 応答は `{redirect_to}` とし、ブラウザの遷移は Web が行う。User MCP は CORS で Web のオリジンだけを許可する。
  - `request_id` は 1 回だけ使える。CSRF 対策として、`/oauth/authorize` で発行した値と同じものを HttpOnly Cookie（`SameSite=Lax`、User MCP のドメイン）にも入れ、`complete` の要求で照合する。
- 認可コードの有効期限は 1 分で、1 回だけ使える。

#### トークン

| 種類 | 形式 | 有効期限 | 保存 |
| --- | --- | --- | --- |
| アクセストークン | ランダムな 32 バイトを base64url にした値（接頭辞 `dmcp_at_`） | 1 時間 | SHA-256 のハッシュ |
| リフレッシュトークン | 同上（接頭辞 `dmcp_rt_`） | 90 日（使うたびに延長） | SHA-256 のハッシュ |

- リフレッシュトークンはローテーションする。使用済みのトークンが再び使われたら、その grant に属するトークンをすべて失効させる（リプレイ検知）。
- JWT は使わない。不透明トークンなら失効が即座に効くうえ、検証は主キー引き 1 回で済むので負荷も問題にならない。
- Firebase でユーザーが削除・無効化された場合に備え、リフレッシュ時に Firebase の `GetUser` で状態を確認する。

#### スコープ

| スコープ | 許可する操作 |
| --- | --- |
| `dotto.read` | すべての参照系ツール |
| `dotto.course_registrations.write` | 履修登録の追加・削除 |
| `dotto.user.write` | ユーザー設定（学年・コース・クラス）の更新 |

- 既定で要求するのは `dotto.read` だけにする。`scopes_supported` にはすべてを載せる。書き込みはクライアントが要求し、ユーザーが同意画面で個別にチェックしたときだけ付与する。
- `tools/list` にはすべてのツールを返し、実行時に権限がなければ `403 insufficient_scope` を返す（クライアントが step-up 認可を行えるようにする）。

### 3. ツール

ツール名は `snake_case` とし、各ツールは対応する `handler.Handler` のメソッドを呼ぶ。
呼び出し前に `auth.WithUser(ctx, auth.User{ID: uid})` を context に入れ、App API と同じ認可境界（ユーザー本人のデータのみ）にする。
入力スキーマは proto の enum を文字列 enum にした JSON Schema を手で定義する。出力は `structuredContent`（`outputSchema` 付き）と、要約したテキストの両方を返す。

| ツール | 呼び出し先 | スコープ | annotations |
| --- | --- | --- | --- |
| `get_my_profile` | `GetUser` | `dotto.read` | readOnly |
| `list_my_timetable` | `ListTimetableItems`（年度・学期） | `dotto.read` | readOnly |
| `list_my_course_registrations` | `ListCourseRegistrations` | `dotto.read` | readOnly |
| `list_cancelled_classes` | `ListCancelledClasses`（自分の履修科目） | `dotto.read` | readOnly |
| `list_makeup_classes` | `ListMakeupClasses` | `dotto.read` | readOnly |
| `list_room_changes` | `ListRoomChanges` | `dotto.read` | readOnly |
| `list_my_calendar` | `ListPersonalCalendarItems`（期間指定） | `dotto.read` | readOnly |
| `list_reservations` | `ListReservations` | `dotto.read` | readOnly |
| `search_subjects` | `ListSubjects`（検索語・学年・コースなど） | `dotto.read` | readOnly |
| `get_subject` | `GetSubject`（シラバス含む） | `dotto.read` | readOnly |
| `list_articles` | `ListArticles`（お知らせ） | `dotto.read` | readOnly |
| `add_course_registration` | `CreateCourseRegistration` | `dotto.course_registrations.write` | idempotent |
| `remove_course_registration` | `DeleteCourseRegistration` | `dotto.course_registrations.write` | destructive, idempotent |
| `update_my_profile` | `UpdateUser`（update_mask 付き） | `dotto.user.write` | idempotent |

- 未実装の RPC（バス・学食）と `RegisterFcmToken` はツールにしない。
- `get_subject` の結果が大きいので、`list_*` は件数の上限（例: 100 件）と要約フィールドに絞って返し、詳細は `get_subject` で取得させる。
- 日付・時刻は JST の ISO 8601 で返す。「今日」「今週」の解釈をクライアントに任せるため、`get_my_profile` の結果に現在日時と今年度・現在の学期を含める。
- handler が返す Connect エラーは、MCP のツール実行エラー（`isError: true`）に変換する。`NOT_FOUND` / `INVALID_ARGUMENT` などはメッセージを返し、`INTERNAL` はメッセージを伏せる。

Resources と Prompts は初期リリースでは提供しない（必要になってから追加する）。

### 4. パッケージ構成

```
cmd/user-mcp/main.go                 # 起動・DI
internal/modules/usermcp/
  server/       # MCP サーバー（go-sdk）とツールの登録
  tools/        # ツールごとの入出力の定義と handler の呼び出し
  oauth/        # AS（metadata / register / authorize / complete / token / revoke）
  bearer/       # /mcp 用の Bearer トークン検証ミドルウェア（uid とスコープを context へ）
  store/        # oauth_* テーブルのリポジトリ
internal/shared/model/oauth.go       # GORM モデル
```

- `internal/modules/appapi/handler` は App API と共有する。`handler.New` の依存（DB、学年暦、microCMS）は `cmd/user-mcp` でも同じように組み立てる。
- `auth.WithUser` / `UserFromContext` はすでに `appapi/auth` にあるので、そのまま使う。

### 5. DB（Atlas マイグレーション）

| テーブル | 主なカラム |
| --- | --- |
| `oauth_clients` | `id`（client_id。DCR は UUID、CIMD は URL）、`client_name`、`redirect_uris`（text[]）、`kind`（`dcr` / `cimd`）、`created_at` |
| `oauth_authorization_requests` | `id`、`client_id`、`redirect_uri`、`state`、`code_challenge`、`scopes`、`resource`、`expires_at` |
| `oauth_grants` | `id`、`user_id`（Firebase uid）、`client_id`、`scopes`、`created_at`、`last_used_at`、`revoked_at` |
| `oauth_authorization_codes` | `code_hash`（PK）、`grant_id`、`redirect_uri`、`code_challenge`、`expires_at`、`used_at` |
| `oauth_tokens` | `token_hash`（PK）、`grant_id`、`kind`（`access` / `refresh`）、`expires_at`、`revoked_at`、`replaced_by` |

- ユーザーと同じクライアントの組み合わせは 1 つの grant にまとめ、再認可したときはスコープを上書きする。
- 期限切れの行は、既存のバッチ（`batch-jobs`）に日次の削除ジョブを追加して消す。
- 将来、Web の設定画面に「接続中のアプリ」（grant の一覧と解除）を出すため、App API に `McpGrantService`（List / Revoke）を追加できる構成にしておく（本設計の範囲外）。

| `MCP_CONSENT_URL` | Web の同意画面（例: `https://fun-dotto.com/mcp/authorize`） |

### 7. インフラ（infra リポジトリ）

- `terraform/google/server/user-mcp/{dev,stg,prd}` を app-api と同じ構成で追加する（Cloud Run、サービスアカウント、Cloud SQL の IAM ユーザー、Secret Manager の参照）。
- ドメインは `mcp.{dev.,stg.,}fun-dotto.com` とし、`cloudflare/domain-mapping.tf` に追加する。
- dev / stg は他のサービスと同じく Cloudflare Access の対象にし、WARP を使う運営メンバーだけが接続できるようにする。アプリ側にメールアドレスの許可リストなどは持たない。
  - そのため dev / stg で検証できるのは、MCP の通信を端末から直接送るクライアント（Claude Code、Cursor、MCP Inspector など）に限られる。
  - Claude.ai（Web / モバイル）や ChatGPT などのコネクタは、トークン交換と `/mcp` へのリクエストを各社のサーバーから送るため、Access で止まる。これらのクライアントでの動作は prd で初めて確認する。
  - Web の同意画面（`/mcp/authorize`）も Access の内側になるが、ブラウザは端末で開くので問題ない。
- DB ロールは `docs/postgresql_roles.md` に従って追加する。`oauth_*` には読み書き、既存テーブルには App API と同じ権限を与える。
- Cloud Run は `min-instances=0` から始める。

### 8. Web（別リポジトリ）

- `/mcp/authorize` ページを追加する。未ログインなら Firebase でログインさせる。クライアント名・スコープ・リダイレクト先を表示して同意を取り、`/oauth/authorize/complete` を呼ぶ。
- クライアント名は自己申告の値なので、「Dotto が確認したアプリではありません」という注記とリダイレクト先のホストを必ず表示する。

## セキュリティ上の考慮

- **トークンの受け渡し（token passthrough）をしない**: User MCP が受け付けるのは自分が発行したトークンだけにする。下流の API にトークンを転送しない。
- **Confused deputy への対策**: 同意は、ユーザーとクライアントの組み合わせごとに必ず Web で取る。`redirect_uri` は登録済みの値と完全一致したときだけ許可する（ループバックはポートだけ任意）。
- **プロンプトインジェクション**: 書き込みツールは対象を ID で受け取り、まとめて削除する操作は提供しない。`destructiveHint` を付け、クライアント側で確認を出せるようにする。
- **レート制限**: `/oauth/*` は IP ごとに、`/mcp` は grant ごとにレート制限をかける（最初はアプリ内のトークンバケット。Cloud Run のインスタンスごとの近似で許容する）。
- **ログ**: トークン・認可コード・ID トークンはログに出さない。ツールの呼び出しは `user_id`、`client_id`、ツール名、結果コードだけを記録する。

## 段階的なリリース

1. AS と `/mcp`、参照系ツールを dev に出し、WARP 経由で Claude Code と MCP Inspector から接続を確認する。
2. 書き込み系ツールとスコープの step-up を追加する。
3. stg で運営メンバーが（Claude Code などで）試用したあと prd に出す。
4. prd で、Web にコネクタの追加手順を載せる前に、運営メンバーが Claude.ai（Web / Desktop / モバイル）と ChatGPT から接続し、OAuth の流れとツールの実行を確認する。問題があれば手順の公開を止めて修正する。
5. Web の「接続中のアプリ」画面を追加する（別設計）。
